# Contributing to Orion OS

Thank you for your interest in Orion OS. This document explains how to
contribute code, branding, tests, and documentation in a way that keeps the
project buildable and reviewable.

## Code of conduct

Be respectful. Be honest about what works and what doesn't. Do not claim a
component is finished if it has not been built and tested.

## Repository conventions

- **One principal UI framework:** Qt 6 / QML. Do not introduce GTK, Electron,
  or other UI toolkits for new Orion-branded desktop components without an
  issue first.
- **One principal package manager:** `pacman`. The Orion Software Center must
  use PackageKit, not raw `pacman` invocations from a GUI process.
- **One principal display server:** Wayland. X11 fallback is documented but not
  the default.
- All custom desktop components live under `desktop/`. Each component is a
  standalone CMake project depending on `orion-framework`.
- Distro defaults live under `distro/defaults/` — copy-on-install, not
  generated by an app at runtime.
- Build scripts under `scripts/` must be **idempotent** and **non-destructive**
  to the host.

## Required tooling

On a real Arch Linux host:

```bash
sudo pacman -S --needed base-devel git archiso calamares \
    qt6-base qt6-declarative qt6-wayland qt6-tools \
    extra-cmake-modules cmake ninja python python-pytest \
    qemu-desktop ovmf
```

Then run `./scripts/setup-build-env.sh` to verify versions and create
symlinks/helpers.

## How to add a new desktop component

1. Create `desktop/<component>/` with at minimum:
   - `CMakeLists.txt`
   - `src/main.cpp`
   - `qml/Main.qml`
   - `org.orion.<component>.desktop`
   - `README.md` with build instructions and dependencies
2. Add a PKGBUILD template in `packaging/orion-<component>/PKGBUILD`.
3. Add a systemd user unit if it should start at login
   (`distro/services/orion-<component>.service`).
4. Add unit tests under `tests/unit/test_<component>.py` (Python) or
   `tests/unit/test_<component>.cpp` (Qt) where logic exists.
5. Add the component's binary name to `distro/archiso/packages.x86_64`.
6. Update `STATUS.md` to reflect the component's state.

## Coding rules (mandatory — see §23 of the project specification)

1. Produce real, buildable code rather than pseudocode.
2. Never fabricate test results.
3. Never claim an application is complete when it is only a mockup.
4. Never silently skip a failed build step.
5. Do not replace existing working project files without inspecting them.
6. Do not expose privileged interfaces unnecessarily.
7. Do not execute commands as root unless genuinely required.
8. Never hardcode secrets.
9. Keep configuration external to application logic where practical.
10. Use version control and meaningful commit boundaries.
11. Write tests for critical functionality.
12. Document dependencies and licensing.
13. Handle errors explicitly.
14. Use maintainable names and modular code.
15. Follow the relevant upstream project's conventions.
16. Do not invent APIs or package names.
17. Verify current upstream documentation before relying on unfamiliar
    functionality.
18. Keep the operating system usable when optional Orion applications fail.
19. Make custom desktop components restartable and diagnosable.
20. Maintain compatibility with normal Arch Linux package-management practices.

## Commit message convention

```
<scope>: <imperative summary under 72 chars>

<optional body explaining why, not what>

<optional footer: Signed-off-by, Refs #123, Breaking-Change: …>
```

Examples:

- `panel: pin running apps via KWin D-Bus instead of polling`
- `archiso: switch to dracut for unified kernel images`
- `docs/security: clarify Secure Boot signing chain`

## Pull-request checklist

- [ ] Builds cleanly with `cmake --build build` for the affected component.
- [ ] `pytest tests/` passes for any touched component.
- [ ] `scripts/security-scan.sh` reports no new high-severity findings.
- [ ] `STATUS.md` updated if the change affects implementation status.
- [ ] No secrets, private keys, or proprietary assets introduced.
- [ ] If the change touches `distro/archiso/`, ISO build path is still valid.

## Licensing of contributions

All contributions are accepted under the licenses described in
[`LICENSE`](LICENSE) and [`NOTICE.md`](NOTICE.md). Contributors retain their
copyright; the project operates under the inbound-equals-outbound model.

## Code review

Maintainers review for: buildability, security defaults, accessibility, and
consistency with the design system. Expect requests for tests and docs on any
non-trivial change.
